# Data files

## `overrides.json`

The Manual Override table (see `CONTEXT.md` and ADR-0002). Hand-edit this when the
upstream feed has a National Team Member at the wrong Club, or is missing them
entirely — most often for the women's squad, whose data upstream is sparser.

```json
{
  "women": [
    {
      "player": "Player Name",
      "clubId": 1234,
      "clubName": "Club Name",
      "position": "Midfielder"
    }
  ]
}
```

- `player` matches on name, case-insensitively. A name that matches an existing
  squad member corrects their Club; a name that doesn't match adds them.
- `clubId` **must** be the club's API-Football team id — that is what the fixture
  lookup keys on. Find it with:
  `curl -H "x-apisports-key: $API_FOOTBALL_KEY" "https://v3.football.api-sports.io/teams?search=CLUB_NAME"`

## `roster.json`

Generated by the daily `npm run refresh:fixtures` and **committed**. Holds both
squads with each National Team Member's resolved Club, so serving a page costs no
roster API calls.

Both squad lists are re-fetched every run, one call each, so a Member who has left
the squad stops appearing and a new call-up arrives the next morning. Everything
but the Club comes from that response; the Club costs a call of its own, so one
already on record is reused rather than looked up again.

A lookup that finds no Club at all — most of the women's squad, whose upstream data
is sparse — is remembered in `clubCheckedAt` and not repeated for a week. Fix those
with `overrides.json` rather than waiting: the retry is only there in case upstream
starts carrying them.

`npm run refresh:roster` rebuilds the same file from scratch and is the tool for a
suspect roster rather than a stale one. It resumes from whatever is already in this
file, so re-running after a rate-limit stop is free. To force a Member to be
re-resolved, delete their entry (or the whole file for a full rebuild).

Don't hand-edit this file to correct a Club — a refresh will overwrite it. Use
`overrides.json` instead, which is layered on top at read time.

## `fixtures.json`

Generated by `npm run refresh:fixtures` and **committed**. Holds each Club's upcoming
matches, so rendering the site costs no API calls at all — see ADR-0003.

Refreshed daily by `.github/workflows/refresh-fixtures.yml`, which needs an
`API_FOOTBALL_KEY` repository secret. Run it by hand after editing `overrides.json`,
since a new club won't have any fixtures stored yet.

Fixtures are stored in their upstream shape rather than already merged, so roster and
override edits take effect on the next render without another API refresh.

`unavailableClubs` lists clubs whose fetch failed during the refresh. The site names
them rather than showing an incomplete schedule as if it were complete. Re-running
the script retries them.

Don't hand-edit this file — a refresh overwrites it.

## `internationals.json`

Generated by the same daily `npm run refresh:fixtures` and **committed**. Holds each
squad's upcoming Internationals — the National Team's own matches — one call per
squad.

They live here rather than in `fixtures.json` because they obey different rules:
no 21-day horizon, both squads listed even when empty, and eventually hand-entered
records merged over fetched ones. Mixing them in would entangle the Club Fixture
staleness logic, which this file leaves alone.

```json
{
  "generatedAt": "2026-09-06T01:54:43.228Z",
  "squads": [
    {
      "squad": "men",
      "teamId": 1113,
      "status": "scheduled",
      "fetchedAt": "2026-09-06T01:54:43.228Z",
      "internationals": [{ "fixture": {}, "league": {}, "teams": {} }]
    }
  ]
}
```

Both squads always appear, whatever happened, and `status` says which of three
things did:

- `scheduled` — Internationals are coming up, and they are in `internationals`.
- `none-scheduled` — the fetch worked and there are none. **This is the women's
  squad's real answer**, not a fault: their qualifying group finished in June 2026
  and nothing has been announced since.
- `unavailable` — the fetch failed. `unavailableReason` says why, `internationals`
  holds whatever was last stored, and `fetchedAt` says how old that is (`null` if
  it was never fetched at all). Re-running retries it.

`none-scheduled` and `unavailable` must never be collapsed into "no matches": one
means there is nothing coming, the other means we do not know.

Internationals are stored in the same upstream shape as Club Fixtures. Two fields
read differently for them: `venue` is always `null`, because the source carries no
venue for national team matches, and `round` is a bare number ("3") rather than a
phrase like "Regular Season - 5".

A record may also carry a `source`. It is absent on everything the refresh fetches,
which means API-Football, so the same credit isn't repeated on hundreds of rows;
a record that names one is published crediting it instead. That is what stops a
match a human took from NFSBiH's announcement being presented as the API's — see
[ADR-0004](../docs/adr/0004-nfsbih-rss-as-second-source-with-per-record-provenance.md).

The app shows the **next International Window** whole rather than the next few
matches: consecutive Internationals belong to the same window while no more than
14 days separate them, and none of it is bounded by the 21-day horizon that keeps
the club feed short. So a break's later matches are visible weeks out, and a break
already under way keeps showing the part still to be played.

Don't hand-edit this file — a refresh overwrites it.
